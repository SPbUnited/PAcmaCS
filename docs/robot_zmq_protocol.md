# FB4: управление роботами по ZMQ

Робот не знает IP управляющего компьютера. Он только открывает два TCP-порта,
а управляющие компьютеры сами подключаются к роботам.

Каждое сообщение состоит из двух ZMQ frames: UTF-8 topic и JSON payload.

## Команды

```text
PC PUB connect tcp://fb4-XX.local:5555
  -> Robot SUB bind tcp://*:5555
topic: cmd/<robot_id> или cmd/all
payload: JSON
```

Робот подписан на адресный `cmd/<robot_id>` и общий `cmd/all`. JSON строится из
существующего объекта команды центрального декодера; к его полям добавляются
`isteamyellow` и `timestamp`.

```text
PC A PUB -------> fb4-00 SUB :5555
PC A PUB -------> fb4-01 SUB :5555
PC B PUB -------> fb4-02 SUB :5555
```

## Телеметрия

```text
Robot PUB bind tcp://*:5556
  -> PC SUB connect tcp://fb4-XX.local:5556
topic: tel/<robot_id>
payload: JSON
```

JSON телеметрии содержит как минимум `robot_id`, `timestamp` и `seq`. Эмулятор
также отправляет `voltage`, `ball_sensor`, `status` и `get_timestamp` последней
полученной команды.

```text
PC A SUB <------- fb4-00 PUB :5556
PC A SUB <------- fb4-01 PUB :5556
PC A SUB <------- fb4-02 PUB :5556

PC B SUB <------- fb4-00 PUB :5556
PC B SUB <------- fb4-01 PUB :5556
PC B SUB <------- fb4-02 PUB :5556
```

Один робот может обслуживать несколько подключившихся компьютеров. Поэтому
несколько компьютеров могут одновременно получать его телеметрию, а разные
компьютеры могут отправлять команды разным роботам. Смена `robot_id` требует
только перезапуска сетевого процесса робота, а не перезагрузки одноплатника.

## Настройка управляющего компьютера

Центральный декодер генерирует hostname всех 16 роботов, от `fb4-00.local` до
`fb4-15.local`. В `config.yml` задаются только порты:

```yaml
control_decoder:
  fb4_port: 10000
  fb4_command_port: 5555
  fb4_telemetry_port: 5556
```

Пакеты UDPie остаются UDP-датаграммами. Номер робота читается из пакета, после
чего центральный декодер отправляет пакет так же, как команды (см. ниже):
роботу по WiFi на `<ip>:10000` или на радио-коробку.

## WiFi или радио-коробка

Декодер выбирает способ связи для каждого робота отдельно, при каждой команде:

- **WiFi** — если у `fb4-XX.local` нашёлся IP и от робота приходила телеметрия
  не позже `fb4_wifi_feedback_timeout` назад. Команды идут protobuf
  `RobotCommand` на `<ip>:5555`.
- **Радио-коробка** — во всех остальных случаях. Команда уходит 13-байтовым
  пакетом (`control_decoder/control_models/footbot4_radio.py`) на
  `fb4_ip_low` для роботов 0–7 и на `fb4_ip_high` для 8–15, порт `fb4_port`.

```yaml
control_decoder:
  fb4_ip_low: "10.0.120.220"
  fb4_ip_high: "10.0.120.221"
  fb4_wifi_feedback_timeout: 1.0 # [s]
```

Через коробку проходят только скоростные команды (`NEW_FORMAT`). RICOCHET,
CATCH_BALL и relocate (GLOBAL_COORDINATES) там пропускаются с
предупреждением, SET_COEFFICIENTS (коэффициенты регуляторов) — молча. Единицы пакета коробки, в которые декодер переводит JSON:

| Поле | JSON | Пакет коробки |
|---|---|---|
| скорость | мм/с | fp8 (1-4-3) в см/с, `velx = -left_vel`, `vely = forward_vel` |
| угловая скорость | рад/с, > 0 против часовой | fp8 в рад/с, со знаком минус (прошивка инвертирует) |
| угол | рад | int8 в π/128 рад, со знаком минус |
| кикер | вольты | уровень 0..15 (1..15 = 100..330 В) |
| дриблер | 0..15 | 0..15 |

При смене способа связи декодер пишет в консоль, например
`[fb4] robot 3: box -> wifi`. В таблице телеметрии COMMAND_DECODER это колонка `link`.

Если коробка выключена или её нет в сети, пакеты в неё выбрасываются. Сокет коробки неблокирующий: иначе, пока ядро ищет её по ARP (~3 с), `sendto` ждёт и останавливает весь декодер. Стратегия шлёт команды и неиспользуемым роботам, а у них нет WiFi, поэтому их пакеты всегда идут в коробку. Ошибки отправки декодер печатает не чаще раза в секунду:
`[fb4] 445 box packets not sent in 1 s (last: robot 1, 10.0.120.220: BlockingIOError(...)); is the radio box on?`.

## Только свежие команды

Каждый проход цикла декодер забирает из входящей очереди все команды стратегии. Для каждого робота каждой команды он оставляет только последнюю и отправляет только её (`drain_inbound` в `control_decoder/main.py`). Сообщения склеиваются по роботам, потому что в одном сообщении могут быть не все роботы. Последний SET_COEFFICIENTS робота хранится отдельно от его последней команды движения: они не затирают друг друга. Если декодер где-то задержится, он не станет потом проигрывать накопившиеся старые команды, и робот не будет ездить по ним после того, как стратегия поменяла решение или остановилась.
